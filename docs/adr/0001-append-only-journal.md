# ADR-0001 — The journal is append-only; corrections are reversals

- **Status:** Accepted
- **Date:** 2026-08-01
- **Supersedes:** —

## Context

A ledger records financial facts. The design question is what happens when one
of them turns out to be wrong.

The obvious approach is to make journal entries mutable: find the wrong row,
fix the amount, move on. It is simple, it matches the CRUD shape every framework
optimises for, and it is what most homegrown ledgers do first.

It also destroys the thing a ledger exists for. If an entry can be updated, then
a balance computed today is not necessarily the balance that will be computed
from the same data tomorrow, and "what did we believe on 30 June" becomes
unanswerable. Every audit obligation, and every debugging session that starts
with "this number was different last week", depends on history being stable.

## Decision

`journal_entry` and `journal_line` accept `INSERT` only. No `UPDATE`, no
`DELETE`, at any layer.

A correction is a **reversal**: a new entry mirroring the original with
directions flipped, linked by `reversal_of_entry_id`, carrying a mandatory
reason. The correct entry is then posted separately. All three facts remain
visible.

Enforcement is layered, deliberately redundant:

1. The domain model exposes no mutator on a posted entry.
2. `REVOKE UPDATE, DELETE, TRUNCATE` on the application's database role.
3. `BEFORE UPDATE OR DELETE` triggers that raise with a message pointing at the
   reversal endpoint.
4. ArchUnit forbids calls to mutating repository methods.
5. Integration tests assert that raw SQL `UPDATE` and `DELETE` fail, and that
   the grant matrix contains only `SELECT` and `INSERT`.

Layer 2 is the real boundary — the role is structurally incapable of issuing the
statement. Layer 3 exists to produce a readable error and to keep protecting the
data if a future migration widens the grant by mistake. Layer 5 is what makes
that mistake fail CI.

The reversal's lines are **generated by the server** from the original. The API
provides no way to supply them, so a reversal cannot be a partial or subtly
different cancellation of the entry it claims to reverse.

## Consequences

**Good**

- History is stable: a balance as of any past date returns the same number
  forever.
- The audit trail is not a parallel table that could drift. The journal *is* the
  audit trail.
- Concurrency gets easier, not harder: append-only writes never contend on a
  row, so no locking is needed on the hot path.
- Replication, backup and change-data-capture all become trivially correct,
  because there are no updates to order.

**Costs**

- Storage grows monotonically. Accepted; for the demo, handled by restoring a
  database branch, not by deleting rows
  ([§8.10](../08-deployment.md#810-demo-data-lifecycle)).
- Correcting a typo in a description requires a reversal plus a repost. Accepted:
  a description is part of the record of what was asserted at the time.
- The UI must show superseded entries rather than hiding them, which is more
  work than rendering a list. This is also the feature — see
  [§6.3](../06-frontend.md#account-movements).
- Users accustomed to editing spreadsheets need the model explained. The error
  message from the trigger does that explaining at the moment it is needed.

## Alternatives considered

**Soft delete (`deleted_at`).** Every query must remember the predicate; the one
that forgets reports a wrong balance, silently. It also does not solve amount
corrections, only deletions.

**Full row versioning (`valid_from` / `valid_to`).** Preserves history, but every
read becomes a temporal query and the accounting semantics of a "version 3 of
entry 41" are unclear to an auditor. Reversals are the domain's own answer to
the same problem, and accountants already understand them.

**Event sourcing the whole application.** The journal is already an event log;
adding a second one around it would be ceremony. Reconciliation state genuinely
is mutable opinion, and forcing it into events would gain nothing.
